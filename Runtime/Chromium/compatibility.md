# Chromium launch acceptance

Pinned candidate: Chromium **156.0.8078.80**. Every mandatory row must pass in the installed, signed build on both native architectures. `U` = untested; `B` = blocked on native browser-layer integration. Neither is a waiver. CEF exploration does not qualify the full Chromium runtime. Site/service and independently authored extension versions must be frozen before a qualification run; none are qualified here.

Use disposable Work and Personal profile UUIDs in **one runtime process**. Two spaces share Work; a third uses Personal. Before testing, the native bridge must supply verifiable UUID → Chromium Profile → tab/window ownership. Separate processes, separate endpoints, directory names and URL labels do not prove that mapping. Never point fixtures at live profiles. Record app/engine build, architecture, OS, fixture versions and concise results in the ticket, not committed logs.

The fixtures are capability probes, not substitutes for independently authored extension qualification. Current fixture: [`profile-extension`](../ChromiumTests/Fixtures/profile-extension), MV3 1.0.0. Its background listener records bounded tab/window/install events and returns a per-worker instance ID. Options UI stores a profile marker and requests an optional example.com grant. Popup increments profile-local storage. `assertions.js` runs inside the extension page after the native host has established ownership:

```javascript
await assertProfileFixture({marker: 'Work', requiredURLs: ['http://127.0.0.1:8769/?space=work-2'], forbiddenURLs: ['http://127.0.0.1:8769/?space=personal'], forbiddenTabIds: [], forbiddenWindowIds: [], optionalOriginGranted: true});
```

For E6, first run `const {observationId} = await chrome.runtime.sendMessage({type: 'reset-observations'})` and wait for its reply. Then create/close known Work, Personal and private tabs/windows. Pass `observationId`, `expectedEvents: [{type: 'tab-created', id: ownTabId}, {type: 'tab-removed', id: ownTabId}, {type: 'window-created', id: ownWindowId}, {type: 'window-removed', id: ownWindowId}]`, and the real foreign tab/window IDs captured by the host, including private IDs, to `assertProfileFixture`. Missing positive events, a mismatched reset or any dropped history fails; reset and repeat a smaller window if the 50-record bound is exceeded. Empty/broken collection cannot qualify E6. Storage-only checks may omit `expectedEvents` and `observationId`. Capture the returned `workerInstance`, verify the worker actually stops, then pass `previousWorkerInstance` after wake. Keeping its inspector open prevents a valid suspension test. No automation install or consent bypass is provided.

For P5, first establish E6 separately. With Work selected, reset both profile installations and retain each `observationId`; capture their tab IDs, logical window IDs and active `{id, windowId}` pairs from the native host. Keep the same NSWindow key while switching Work → Personal → Work without changing selected tabs. Work must observe `[chrome.windows.WINDOW_ID_NONE, workWindowId]`; Personal must observe `[personalWindowId, chrome.windows.WINDOW_ID_NONE]`. Pass this as `expectedFocusSequence`, plus foreign IDs, `assertStableTabsAndWindows: true`, and the initial `expectedTabIds`, `expectedWindowIds`, `expectedActiveTabs`. Do not introduce E6 creation/removal traffic into this observation window. Empty focus history, synthetic activation/lifecycle events or changed identities fail. At each stop, separately assert `expectedCurrentWindow` and `expectedLastFocusedWindow` with the owning logical `{id, focused, state}`; capture explicit API errors instead of replacing them with another profile's window. Collect observations without activating an extension inspector or popup. Repeat native deactivation and real action-popup parenting as separate cases. These probes still require native ownership, visibility, keyboard/IME and live-document checks to qualify P5.

For P5/E9 command ownership, verify `chrome://extensions/shortcuts` assigns the fixture's `profile-command-probe` to Command+Shift+Y in both synthetic profiles. Reset both logs, retaining each reset ID and real foreign IDs. With Work selected, send the native shortcut once; require `expectedCommands: ['profile-command-probe']` in Work and `expectedCommands: []` in Personal. Reset and repeat with Personal selected, reversing expectations while the same NSWindow stays key. Both positive observations are required; two empty logs cannot qualify. Invoking the handler directly does not test keyboard dispatch. Keep this separate from E6 lifecycle traffic.

For P5/E9 shared-window controls, keep Personal selected while a Work extension updates bounds through its own window ID. Require the actual shared native bounds in both profiles' queries and bounds events containing only each recipient's own ID; Personal's selected tab and focus remain unchanged. Reject a request using Personal's ID from Work. A Work `focused: false` request while Work is inactive must leave Personal focused; `focused: true` must select Work before native activation. Check minimize/restore and fullscreen separately. Fullscreen must retain the requesting extension/profile attribution and enforce the applicable policies, including denial and exit. Independent cached window geometry, silent ignored updates, foreign IDs and success replies without the requested state do not qualify. The current fixture does not yet automate these operations.

Serve the site fixture on the same loopback origin for all profiles and restarts (from the repository root): `python3 -m http.server 8769 --bind 127.0.0.1 --directory Runtime/ChromiumTests/Fixtures/site`. Install the extension through the intended ordinary UI in synthetic Work; set marker Work in options; open that origin in both Work spaces and Personal. Save site marker in Work, read it in the other Work space, verify absence in Personal, quit fully and repeat. Then separately install in Personal, set marker Personal and repeat E2. Retain extension ID/signing key during updates; package generation and host registration stay outside source commits.

For native one-shot testing, register `native_echo.py` only in an isolated test host-discovery root, with an executable absolute path. Create one host manifest allowing this extension's exact `chrome-extension://ID/` origin, and another denying it. From the extension document, call `chrome.runtime.sendMessage({type:'native-probe',host:'HOST_NAME'})`; the allowed response must echo the stored profile marker, the denied result must contain an error. Repeat in both profiles. This does not qualify vendor discovery, signature expectations, ports or deletion cleanup.

The pinned Bitwarden Desktop 2026.10.4 [manifest generator](https://github.com/bitwarden/clients/blob/94f753799058775f04190d6083d33692d7e59645/apps/desktop/src/main/native-messaging.main.ts) registers known browser directories, including Chromium but not Barc. Chromium 156's [POSIX discovery](https://chromium.googlesource.com/chromium/src/+/fb096c0011f9d50f0a264a9376420cdea9c421e3/chrome/browser/extensions/api/messaging/launch_context_posix.cc) searches its user-data `NativeMessagingHosts` directory and configured system directory, without a Chrome-directory fallback. Resolve vendor registration/discovery for Barc's final data root and test a clean installation without Chrome. Bitwarden's `BITWARDEN_CHROME_PROFILE_DIR` override can stage an isolated manifest for a protocol probe; that does not qualify ordinary installed discovery.

A separate Chromium user-data directory does not isolate the vendor desktop app: Bitwarden's [release IPC path](https://github.com/bitwarden/clients/blob/94f753799058775f04190d6083d33692d7e59645/apps/desktop/desktop_native/core/src/ipc/mod.rs) uses its macOS App Group container, with a cache fallback; its socket-directory override is compiled out of release builds. Use a dedicated disposable macOS account and vault for the vendor workflow. Preserve the vendor binary/signature and normal permissions. Biometric success additionally requires Touch ID-capable hardware; a missing-capability result does not pass that case. Package inspection alone qualifies none of these workflows.

D1 requires the complete Chromium app/framework layout, including versioned Helpers, Libraries and Resources: pinned `chrome/app/chrome_exe_main_mac.cc` resolves framework/renderer libraries relative to each executable and initializes helper seatbelts before loading them. The existing release script copies only Xcode's Nook app; it does not stage this engine. Follow pinned `chrome/installer/mac/signing/parts.py` for per-executable signing and renderer/GPU JIT entitlements, then apply the app's separate provisioning/CloudKit entitlements to the parent. The existing Sparkle-only signer and CI's blanket `codesign --deep` are insufficient for this candidate. For a universal artifact, use the pinned `chrome/installer/mac/universalizer.py` merge rules, preserve both architecture-specific V8 context snapshots, and inspect every nested Mach-O; Xcode's `ARCHS` does not merge separately built engines. These are unresolved distribution requirements, not signed-build evidence.

The media candidate must use `proprietary_codecs = true` and `ffmpeg_branding = "Chrome"` while retaining Chromium product branding. This enables additional codec build paths; it does not establish playback, hardware acceleration or distribution readiness. The initial unmodified-source build uses upstream codec defaults and cannot qualify these additional paths.

[Pinned media inputs](../ChromiumTests/media-fixtures.json) identify seven upstream clips by source revision, path and hash, plus an AV1/Opus WebM lossless remux with a pinned recipe and output hash. These short clips support initial format and seek checks; packet preservation does not qualify playback or A/V synchronization.
