# Contributing to Bark

This guide covers building Bark, verifying a browser change and submitting a pull request.

## AI Assistance Notice

If you are using any kind of AI assistance to contribute, this must be disclosed in your pull request, commit, or issue, including the extent to which AI assistance was used (e.g. docs only vs. code generation). If PR responses, commit messages, or comments are being generated by an AI, please disclose that as well.

As a small exception, trivial tab-completion doesn't need to be disclosed, so long as it is limited to single keywords or short phrases.

When using AI assistance, we expect contributors to understand the code that is produced and be able to answer critical questions about it. It isn't a maintainer's job to review a PR so broken that it requires significant rework to be acceptable.

Please be respectful to maintainers and disclose AI assistance.

## Development Setup

You need a Mac and Xcode 26 or later. The package tests and native command-routing check run on Apple Silicon or Intel. Intel has a verified runtime pin and signed-app smoke. The native Apple Silicon runtime pin is pending.

1. **Check out the Bark revision you want to build.** Run the commands below from the repository directory containing `Bark.xcodeproj` and `scripts/bark-check.py`.

2. **Install the Metal Toolchain** for the app’s shader
   ```bash
   xcodebuild -downloadComponent MetalToolchain
   ```

3. **Open in Xcode**
   ```bash
   open Bark.xcodeproj
   ```
   Choose the shared **Bark** scheme. Xcode resolves the Swift packages the first time the project opens.

4. **Build and run Bark.** Install the pinned SDK for your Mac and use the signed build command below. It builds the Swift shell and outer app from the tracked sources, verifies the embedded engine, and places the finished app at `build/Bark.app`. The output directory can start empty. [Native command routing and signed Bark](#native-command-routing-and-signed-bark)

   Space sync's record types live in `scripts/cloudkit/schema.ckdb`. CloudKit refuses a save that carries a field the Production environment lacks, so before every release run `scripts/cloudkit/check-production-schema.sh path/to/management-token` (a CloudKit management token from CloudKit Console → Settings → Tokens & Keys). It lists what Production lacks and fails; then import the schema with `scripts/cloudkit/import-schema.sh path/to/management-token`, deploy it to Production in CloudKit Console, and run the check again.

There is no app test target. Logic with its own checks lives in `Checks/` folders beside each package's sources and in `scripts/tests/`; each file says how to run it. Every package with a `Tests/` folder has a `swift test` suite, and CI runs them on each pull request.

### Native command routing and signed Bark

From a clean checkout, run the native command-window regression without an engine artifact.

```fish
python3 scripts/bark-check.py interaction
```

The regression compiles the shipped command-routing code and checks it against real AppKit windows and a sheet. CI runs it after the Swift package tests.

To check the app entry point and SDK tools on a Mac with Xcode, run the same
commands as the hosted package job. The bootstrap suite compiles small engine
fixtures and older app entries from Git history. A regular clone contains those
revisions. These tests run before a full Chromium build is available.

```fish
python3 -B -m unittest discover -s scripts/tests
python3 -B -m unittest discover -s Runtime/Chromium -p 'test_*.py'
python3 -B -m unittest discover -s Tests/Shared
python3 -B Tests/ChromiumAppShim/check.py
```

Run the catalog, startup focus, page ownership and extension action regressions against the Debug shell on the host architecture. These commands build the shell framework using the SDK headers and locked package versions. The test bridge supplies engine calls. Xcode caches the framework under `~/Library/Caches/BarkSDK/native-checks/`.

```fish
python3 scripts/bark-check.py catalog
python3 scripts/bark-check.py page-host
python3 scripts/bark-check.py profile-pages
python3 scripts/bark-check.py extension-actions
```

With Xcode and a local Developer ID Application identity, build a signed Bark app from a clean checkout. Supply the engine artifact matching the committed SDK pin for your Mac. The [engine recipe](Runtime/Chromium/README.md#checkout-and-build) also builds the SDK from its pinned sources. Xcode resolves the committed package lockfile.

```fish
python3 scripts/bark-check.py engine --install --engine /path/to/Engine
set -lx BARK_SIGN_IDENTITY 'Developer ID Application: Your Name (TEAMID)'
python3 scripts/bark-check.py build
python3 scripts/bark-check.py smoke build/Bark.app
python3 scripts/bark-check.py launch build/Bark.app
```

`build` creates its output directory, compiles the Release shell, stages the pinned engine and signs the app locally. A successful rebuild replaces `build/Bark.app` after verification. Quit that copy before replacing it. Temporary compilation, staging and signing files are removed at the end of each build. Use `--output /path/to/Bark.app` to choose a different destination. Local signing leaves notarization to the distribution workflow.

To verify an existing signed app, use `python3 scripts/bark-check.py verify /path/to/Bark.app`.

`--engine` accepts a directory, a tar archive, or an HTTPS tar archive with the engine files at the root or under `Engine/`. Use Python with the `tarfile` data extraction filter for archives. You can also use `BARK_ENGINE_SOURCE` or the ignored `Packages/BarkEngine/RuntimeArtifacts/<architecture>/Engine/` directory.
Existing Intel artifacts in the former `macos-x86_64/Engine/` location remain usable. The install command keeps a verified copy under `~/Library/Caches/BarkSDK/<pin>/Engine`. A fresh checkout can then build using that pin. The verifier compares the signed app’s embedded files with the selected SDK.
If a cached engine is incomplete, repeat `engine --install --engine /path/to/Engine` with a matching SDK directory or archive. Bark verifies the replacement before switching the cache to it.
To transfer the pinned SDK to another Mac, export it on the build machine and install it on the receiving machine from a checkout with the same pin.

```fish
python3 scripts/bark-check.py engine --arch x86_64 --archive ~/Downloads/BarkSDK-x86_64.tar.gz
python3 scripts/bark-check.py engine --arch x86_64 --install --engine ~/Downloads/BarkSDK-x86_64.tar.gz
```

The export checks the finished archive against the checkout before creating the requested file. Add `--require-official` on both machines to require an optimized engine with verified build provenance.

A successful **Prepare Bark Candidate** run makes its verified SDK available as
a separate Actions artifact for 14 days. When a matching official candidate
exists, use its run ID and the checkout’s pin to obtain the SDK. Enter the
numeric run ID when prompted.

```fish
read -P 'Candidate run ID: ' run_id
set -l arch (python3 scripts/chromium_sdk_layout.py native-arch)
set -l pin (python3 scripts/chromium_sdk_layout.py digest Packages/BarkEngine "$arch")
set -l sdk "BarkSDK-$arch-$pin"
set -l download (mktemp -d)
gh run download "$run_id" --repo kuzaxak/Nook --name "$sdk" --dir "$download"
python3 scripts/bark-check.py engine --arch "$arch" --require-official --install --engine "$download/$sdk.tar.gz"
```

The SDK headers build on Intel and Apple Silicon. Engine install and export, build,
verification, and packaging default to the Mac’s native hardware architecture, even
when Python runs under Rosetta. Use `--arch x86_64` or `--arch arm64` to work with
artifacts for another architecture. The checkout needs a pin for the selected
architecture. The ARM64 runtime pin is still pending.

`smoke` and `launch` require a pinned engine matching the host’s native architecture. `smoke` opens a loopback fixture, waits for the renderer to acknowledge it, then stops Bark. For hands-on work, use `launch`. It keeps the fixture available and Bark running until you quit Bark or press Ctrl+C in the terminal. Both commands remove their disposable profiles when they finish.

For the optional CI smoke, choose a trusted Mac with a logged-in desktop session and a verified SDK pin for its native CPU. Set `BARK_SMOKE_RUNNER` to a runner label unique to that configuration and `BARK_ENGINE_SOURCE` to the matching SDK directory or archive. Set `BARK_SIGN_IDENTITY` to build the checked-out revision on that runner, or supply an existing signed app using `BARK_SMOKE_CANDIDATE`. In **macOS Package Tests**, the configured job runs on pushes to the default branch and manual runs on that branch. It checks the supplied candidate against the checkout's engine pin before running the smoke.

### Run the signed UI walks

From the repository root, install the macOS Python bindings in a virtual
environment you can reuse across checkouts. This setup uses Python 3.13. Run
the walks on an idle desktop with macOS Accessibility and event-posting access.
Individual walks list any additional permissions they use.

```fish
set -l walk_env "$HOME/Library/Caches/BarkSDK/signed-walk-python"
python3.13 -m venv "$walk_env"
"$walk_env/bin/python" -m pip install -r Tests/Shared/requirements-macos.txt
source "$walk_env/bin/activate.fish"
```

The two-profile walk opens the same inbox in Work and Personal. It checks
which tab receives typed input and which page receives the decision on a
pending location request. [Run the two-profile walk](Tests/ChromiumProfilePages/README.md)

The shipping address walk submits two forms, accepts one save prompt, declines
the other, and checks what Chromium retained after quit.
[Run the address walk](Tests/ChromiumAddressSave/README.md)

The extension walk installs a local fixture, opens its pinned action from
both toolbar positions, and exercises Cancel and Remove in Manage Extensions.

```fish
python3 Tests/ChromiumExtensionActions/walk.py --verify-sdk --app build/Bark.app --output (mktemp -d)/extensions
```

The [installed update walk](Tests/ChromiumUpdate/README.md) exercises a signed
disk image and restores a saved draft through an actual app update.

The signed quit walk holds the disposable app’s Network Service during its
ten-second shutdown flush and checks the exit status and remaining helpers.

```fish
python3 Tests/ChromiumQuitSave/walk.py --app build/Bark.app --output (mktemp -d)/quit
```

To measure first input and return to a parked tab on an official candidate,
install its pinned native SDK and run the startup walk on the same Mac.
Grant Screen Recording access to the process running the walk, in addition
to Accessibility and event-posting access.
The walk checks the signed app against the SDK before timing and records
the verified SDK digest with the measurements. For local measurements
with a pinned developer SDK, use `--verify-sdk` in place of `--require-official`.
Exit status 3 means the desktop became unavailable, for example when the
pointer moved between test inputs. Use a completed run for timing.

```fish
set -l evidence (mktemp -d /private/tmp/bark-timing.XXXXXX)
python3 Tests/ChromiumStartup/walk.py --app build/Bark.app --require-official --output "$evidence/startup"
```

### Prepare a Bark distribution candidate

The manual **Prepare Bark Candidate** workflow uses the architecture's pinned official SDK. It checks the build receipt and embedded framework before signing, then uploads the notarized, stapled DMG and Sparkle appcast for review. Feed and download publication are separate release steps. The public Nook transition feed uses the existing Nook release workflow.

Configure the `bark-candidate-x86_64` or `bark-candidate-arm64` environment with required approval and a default-branch deployment restriction. Set `BARK_ENGINE_SOURCE` to the architecture’s pinned engine directory or archive. Set `BARK_SIGN_IDENTITY` and `BARK_NOTARY_PROFILE` to a Developer ID Application identity and notarytool profile on the dedicated runner. Use the existing Sparkle private key as the environment secret `SPARKLE_SIGNING_KEY`. An unavailable architecture pin stops the build.

With `--notary-profile`, packaging also checks Gatekeeper's assessment of the
finished disk image and a fresh copy of Bark from a private, read-only mount.
It verifies the copied app's signature, release metadata and pinned SDK before
assessing execution trust. A failed check leaves the release export unpublished.

Use a separate runner with the matching `bark-candidate-x86_64` or `bark-candidate-arm64` label, Xcode 26 and its Metal Toolchain installed. Before connecting it, install [the runner guard](scripts/runner/job-started-hook.sh) outside the runner’s work directory. Point `ACTIONS_RUNNER_HOOK_JOB_STARTED` at an executable wrapper outside the checkout. Use the installed guard path and the exact protected default ref.

```bash
#!/bin/bash
exec "$HOME/actions-runner-bark/hooks/job-started-guard.sh" --bark-candidate refs/heads/pawl-dev
```

The runner-side guard permits only this repository’s Bark candidate workflow on that ref. Keep the signing runner separate from PR jobs and the legacy Nook release runner. The [local packaging commands](Runtime/Chromium/README.md#prepare-bark-distribution-files) use the same checks.

## Code Style & Standards

### Conventions

- Follow existing SwiftUI/AppKit patterns in the codebase
- Use the established file organization structure
- Use the design tokens in `Packages/NookDesign` for sizes, spacing, colors, fonts and animations instead of literal values
- Prefer modern Swift/SwiftUI APIs when possible

### Compatibility & OS Versions

- **The app’s minimum deployment target is macOS 15.5 (Sequoia).** Do not add `#available` guards for versions below it.
- **APIs newer than macOS 15.5** (macOS 26 and 27) need an `#available` check with a Sequoia fallback.

## Pull Request Process

### Before You Start

- Check existing pull requests for related work. Discuss substantial changes with the maintainers before implementation. [Bark pull requests](https://github.com/kuzaxak/Nook/pulls)
- Keep each pull request focused on one feature or fix.

### Creating Pull Requests

1. **Create a topic branch from the Bark revision you are changing.** The SDK-based build commands require a checkout containing `scripts/bark-check.py`.

   ```fish
   git switch -c feature/your-feature-name
   ```

2. **Make your changes** and commit them with clear, descriptive messages

3. **Push to your fork**:
   ```bash
   git push origin feature/your-feature-name
   ```

4. **Open a pull request against the published branch your change builds on.**
   - Provide a clear description of the changes
   - Reference any related issues
   - Include screenshots or videos for UI changes
   - List any new or changed text a user will see, so it can be reviewed
   - Disclose any AI assistance used (see AI Assistance Notice above)

5. **Respond to review feedback** promptly and constructively

## Reporting bugs and requesting features

The fork currently accepts pull requests. When proposing a fix or feature, include the details below in the relevant pull request. [Bark pull requests](https://github.com/kuzaxak/Nook/pulls)

### Bug Reports

Be descriptive and thorough. Include:

- **macOS version**
- **Bark version and build number**
- **Clear steps to reproduce the issue**
- **Expected vs actual behavior**
- **Screenshots if applicable**
- **Relevant console/error messages**

### Feature Requests

Provide detailed context. Include:

- **Clear description of the feature and its use case**
- **Explain how it improves the Bark browsing experience**
- **Consider implementation complexity and user impact**
- **Check that similar functionality doesn't already exist**

## Community Guidelines

- Be respectful and constructive
- Help maintain a welcoming environment for all contributors
- Focus on the code and ideas, not individuals
