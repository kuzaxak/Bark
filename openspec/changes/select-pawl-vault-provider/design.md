# Design

## Context

Bark's native engine already reports parsed password and OTP fields, validated submissions, and Chromium WebAuthn requests through its C SDK. Swift's existing VaultService presents the choices, speaks the Pawl v1 socket protocol, and checks ownership again when a reply arrives. Pawl validates the peer's macOS audit token and code signature before servicing credential requests. This is a shared user vault. A profile UUID binds a browser operation to its page. Pawl's v1 server selects entries from its unlocked database by site and does not partition the database by browser profile.

Pawl Vault build 7 recognizes the exact signed Nook identifier and rejects the correctly signed Bark identifier. The pinned engine also returns to Chromium when a connected Pawl observer does not claim a save offer. The earlier migration design intentionally retained that fallback. The shell now routes the Profiles password control to the running provider. Selecting Pawl as the exclusive manager also requires the engine to enforce the choice.

## Goals

Give the existing opt-in a consistent meaning on normal launch, after an unlock and during a page or profile transition. Keep native input, modal passkeys, external security keys, and the existing signing and SDK model. No credential migration is necessary.

## Options considered

| Option | Fit for this project |
| --- | --- |
| Complete the native integration | Reuses the existing signed peer, Chromium's field and submission identities, its WebAuthn request lifetime, and Bark's native picker. Requires a companion trust update and provider routing in the engine. Selected. |
| Port the WebKit form and passkey scripts | The WebKit adapter uses an isolated script world for forms and a page-world shim for passkeys. Porting those scripts would leave Chromium free to fill a saved login or write a submitted one. Chromium already supplies the frame, field and request identities needed by the shared Swift service. |
| Build a Chromium extension and native-messaging host | Adds an extension, host registration, permissions and another identity per install. It would duplicate existing field and passkey integration. Keep interoperability with deliberately installed extensions. |
| Rely on Apple's system Autofill or a Chrome policy | Platform Authenticators remain valuable separate choices, but this does not route every Bark save, OTP and prompt through Pawl. Chromium's PasswordManagerEnabled policy can still fill previously saved passwords. |

## Decisions

1. **Provider choice and engine startup.** Keep the existing app-wide opt-in and its current default. Publish the chosen provider before Chromium starts serving documents, independent of vault connection status, active window or per-page observers. Apply preference changes on the next full relaunch. The running browser keeps its launch-time provider, and Settings names it when a change is pending. This avoids transferring an in-flight lookup, generated credential or queued write between managers. Append a single pre-start operation to the versioned C table. Build and pin the matching SDK through the tracked recipe. Keep all Chromium C++ types behind the C boundary and changes within the project's reviewed patch budget. An incompatible SDK must not advertise exclusive mode.
2. **Separate form recognition from stored credentials.** Keep Chromium parsing, submission validation, navigation/redirect checks and document-bound field capabilities. Suppress built-in suggestions, automatic fill/sign-in, password generation, manual fallback, save/update UI and writes at the sites that deliver Chromium credentials or commit them. Include Credential Management API and generated-password paths. Do not disable form parsing or rely on a single disabled save bubble. Preserve managed policy, origin restrictions, address/card Autofill and standalone security keys. Apply selection before first navigation, including new, private and unattached tabs. Termination ends the current provider’s browser requests. An already-authorized Pawl write can finish in Pawl.
3. **Keep the trust boundary.** A separately shipped Pawl change can admit the exact Bark and legacy Nook identifiers under the approved Apple signing team. Both apps check the code of the socket peer. Identify the client in consent copy from the verified identity. Never authorize using the hello string, a path, a team-wide wildcard or a persisted hash exception. Preserve owner authentication, process/database/lock-epoch binding, and signed-server verification. Check socket access on supported macOS using the shipped entitlements before considering any entitlement change. Keep database access with Pawl.
4. **Capture the right interaction.** Require genuine field interaction before opening the chooser, plus explicit credential selection to fetch the password or code. Preserve cross-origin frame identity, foreground view and profile through async replies. Under the proposed private-window policy user-invoked fills may use the shared vault, with ephemeral browser state and no save/update offers. Agent and verification sessions retain their existing isolation. Do not promise separate vault databases for Work and Personal.
5. **Authorize the exact write.** Bark asks the connected provider to prepare a create or update using the original site, username and profile. One exact update target yields an Update card. Several matches route to manual management. A provider that lacks conditional writes gets manual management for new accounts as well. Bark uses the same rule with both Chromium SDK generations. Opening Pawl passes no site or password.
6. **Keep WebAuthn on its native path.** Pawl is an existing modal authenticator. Preserve Chromium's relying-party/origin checks, client-data hashes, user presence, ES256 bounds and cancellation. In Pawl mode suppress competing browser-managed password/passkey-provider offerings while leaving explicitly selectable hardware and other independently supported external authenticators available. Conditional account suggestions require separate Chromium integration and qualification before claiming WebKit parity.
7. **Show who owns passwords.** Privacy settings identifies the selected manager, vault status and recovery steps. Profiles routes Password Manager to the selected provider, independent of the active browsing space. Cover direct Chromium password-manager URLs, aliases and password context menus as additional entry points. Existing Chrome credentials remain available if the user explicitly selects Chromium again. A provider that refuses the client is distinct from a locked vault or a failed verification of the vault itself.

## Qualification and rollout

Use the existing synthetic vault, receipt-pinned engine and disposable profiles. Seed a synthetic Chromium credential alongside a different Pawl credential for the same site. Exercise cold launch, a disabled preference, locked/disconnected/untrusted Pawl, recovery, two profiles, private browsing, redirect, split/Peek ownership, and change the preference during an outstanding request, then verify the next launch. Verify the delivered field value, the selected entry and write counts in both stores. Check normal address/card paths independently. Use a disposable signed Pawl database on Intel and Apple Silicon for the process handshake, OTP, approved update, and relying-party verification of a signed passkey ceremony. Hardware keys and conditional UI require their own evidence. Do not log secrets or export a user's database.

The provider-capable engine recipe is on `codex/pawl-engine-candidate`. Its recipe touches 290 upstream files, with 978 hunks, 12,612 added lines and 24 upstream test files. The ceilings remain 291, 982, 12,614 and 24 respectively. Eight patches for the retired Chromium window were removed. The regression for a shared window surviving an inactive profile's closure now checks both Bark profile clients, their prompt anchors and the surviving document in the same physical window. The integration branch still consumes the previously pinned SDK. Publish a provider-capable SDK only after the linked runtime and signed pair pass qualification. [Patch budget](../../../Runtime/Chromium/BUDGET.json)

**Field gestures.** The Autofill observer reports the same field identity after a page calls `focus()` and after a mouse click. Chromium's existing `OnFocusChangedInPage` callback also supplies Blink's focus cause and the DOM node ID in its originating document. Match a mouse or Tab focus transition to the parsed password or OTP field using both identities. Scripted focus cannot open the chooser. Provide a deliberate native keyboard action on the verified focused field for sites that autofocus it and for reopening a dismissed chooser. Verify top-level documents, embedded frames, both split panes and a focus change during lookup. This approach uses Bark's native adapter and avoids changes to the Chromium renderer IPC protocol.

**Credential selection.** The native field token identifies the document and field. Bark also keeps the entries presented to the user. A password fetch targets the chosen entry ID and the reply must carry the original username, compared before display formatting. The one-time-code method returns only a code, so Bark checks the selected entry against the entries offered for that field before requesting it. For passkeys, the relying party can allow several credentials or leave discovery open. Bark filters the picker against that request and verifies the assertion carries the credential ID the user picked.

**Concurrent writes.** Pawl v1 chooses the first exact host and username match at the time of `save`. A login that looked new at browser consent can overwrite a concurrently created entry. A v1 server also ignores unknown fields on `save`. The Chromium client therefore uses two distinct methods when Pawl advertises `conditionalLoginWrites` in its existing v1 `hello` reply.

| Step | Contract |
| --- | --- |
| Prepare | `prepareLoginWrite(origin, username, profile)` returns `create` or `update` and an opaque one-use ticket. `ambiguous` gives Bark a manual management action. Preparation sends no password. |
| Consent | Bark shows the site and account for the original validated submission, including after a redirect. Owner loss before dispatch cancels the action. |
| Commit | `commitLoginWrite(origin, username, profile, password, ticket)` requires fresh owner approval in Pawl. A `saved` reply acknowledges durable persistence. A `conflict` reply guarantees that the database and its pending writes are unchanged. |
| Recovery | Expiry, ambiguity and concurrent edits require fresh consent or manual management. A lost reply produces a local notice to check Pawl. Bark sends each approved commit at most once. A commit already dispatched can finish in Pawl after the browser tab closes. |

The companion must bind the ticket to the verified connection, process, unlocked database and lock generation, exact request context, and the original match. Exact write candidates can differ from the broader site suggestions in the picker. Use a bounded ticket cache with monotonic expiry. Spend the ticket before owner authentication, then validate all bindings again, including writability. A create still needs an absent entry. An update still needs one exact match with the same identity and revision.

Pawl's v1 handler mutates the in-memory database before the viewer checks for a save already in progress. A conditional commit needs to reserve the writer before mutation or journaling. Revalidate the condition if a journal operation is replayed or a conflict is resolved. Return an unconfirmed result if persistence is uncertain. The Bark repository exercises the message and consent contract against a disposable in-memory implementation. Durable save, owner authentication and live connection binding are companion qualification work.

Check the website Credential Management API, Chrome's Touch ID and enclave paths, and password context menus alongside the visible form picker. Enterprise password-reuse protection has its own policy and must be tested separately from the user's choice of a password store.

**Other management entry points.** Chromium's password-manager WebUI serves the `chrome://password-manager` host, its subpages and its installed web app. The browser normalizes `about:password-manager` to the same host. Route these to Pawl management before the stock controller attaches. Chromium Settings also has access to the `passwordsPrivate` API, including password CSV import and export. Gate the browser-side credential delegate. In the page context menu, filter password selection, generation and import at construction and dispatch, while keeping address, payment and hardware-key commands available. Preserve enterprise password-reset warnings.

The pinned macOS general browser-data importer already excludes passwords. Both Settings and first-run import intersect the requested fields with the source's supported fields. On macOS the Firefox source excludes passwords, and Safari and HTML files support bookmarks only. Bark's native onboarding importer skips passwords as well. Recheck this assumption when updating Chromium. A password-manager CSV import is a separate operation.

Ship the narrowly compatible Pawl companion first. Offer exclusive mode in a Bark build whose engine implements the routing contract. Retaining the setting while a vault is being updated must never silently switch the user back to Chromium. Reverting the selection restores Chromium for future requests without moving either provider's data.
